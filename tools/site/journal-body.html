The problem

A cloud flow in Power Automate signs in to services like Outlook or SharePoint through a connection. A connection usually belongs to the person who created it. When that person leaves and IT blocks their sign-in, every flow that runs on their connections starts failing.

Adding a co-owner is the common advice for keeping a flow alive. A co-owner can edit the flow, but the flow keeps running on the original owner's connection until someone swaps it. In my test, a co-owned flow failed on its first run after the owner's sign-in was blocked and kept failing, still switched on, for more than a day.

Microsoft already helps after the fact: recommendations for orphaned flows, an API to reassign agents, and an Agentic Center of Enablement in preview that finds resources without an owner. What I could not find is a list prepared before the last day, saying "these flows run on this person's login and will break".

What the tool will do

An admin enters the person who is leaving. The tool lists every flow that runs on that person's connections, across environments, including flows inside solutions, and separates them from flows the person only co-owns. Read-only. Nothing is changed, and nothing from the tenant is kept outside the admin's own machine.

How I test

Every claim is checked against Microsoft's own screens. I write down what I expect before the test runs, then compare it with the run history Power Automate shows.

  • A Microsoft 365 Business Basic trial tenant with four accounts: an admin, two makers and one leaver.
  • Six flows, each built to show one pattern: the leaver's own login, a co-owner, a co-owner who swapped in their own login, a control flow by another maker, a SharePoint flow, and a flow inside a solution.
  • The test step is the one IT usually takes first on a last day: Block sign-in in the Microsoft 365 admin center. Nothing else is changed.

  • 6 of 6 outcomes matched. My timing was wrong: I expected failures within about 90 minutes, and the Outlook flows failed on the first run after the block, six minutes later.
  • The error points elsewhere. The failed step reads "Unauthorized", and the banner says the connection "needs to be signed-in again" and that "the most common cause is a changed password or a policy set by your tenant administrator". It doesn't mention that the owner has left, and signing in again as that person isn't possible.
  • The co-owner wasn't told. The co-owner got an email when they were added. Over the next day there was no email to them about L-02 failing. A failure summary that did arrive listed only a flow where they were the primary owner. That is one observation, to be confirmed.
  • Still open: why L-05 succeeded once at 20:15.

What the admin center shows

I checked Maker inventory in the Power Platform admin center by hand on 21 October, a day after the block.

  • Owner, not login. The available columns cover owner, creator, last modified by, connector type, environment and status. None shows whose connection a flow runs on.
  • One false alarm. Filtering by the leaver as owner gives 5 flows. Only 4 broke. L-03 is owned by the leaver but runs on the co-owner's login, so it kept working.
  • Status. Every flow showed "Activated", including the four that had been failing for a day.
  • Recommendations. The Actions page listed 7 recommendations, none about these flows or the blocked user.
  • Agentic Center of Enablement. The preview is meant to switch on once a managed environment exists. I turned one on; about 20 hours later its pages had not appeared in this trial tenant, so I couldn't test whether it would flag these flows. It is a preview and may simply not have reached the tenant yet.

Can a tool see it coming?

The second question was whether an outside tool can find these flows before anyone leaves, using only public admin APIs and read access. Prediction, written at 21:55 on 21 October: it should name L-01, L-02, L-05 and L-06 and nothing else.

The script listed exactly those four, left out L-03 and L-04, and resolved the solution flow's connection reference to the leaver's connection. All four were still shown as started after a day of failures.

The first version signs in through a browser as an admin and reads environments, flows, connections and connection references. A sign-in that uses a code typed on another device was blocked by the tenant's security defaults, so the script uses a normal browser sign-in.
